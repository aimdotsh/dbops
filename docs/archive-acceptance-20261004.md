# tx124 MySQL 数据归档验收

记录日期：2026-10-04。测试对象是 tx124 的 MySQL 8.0.46 实例 #5，端口 13310。测试只使用新建的 `dbops_archive_validation_20261004_01` schema，不修改已有业务表。测试数据保留在实例中，供页面和 SQL 复核。

## 操作与结果

在 `events` 表写入 2,000 行。ID 1～1,200 的 `created_at` 为 2026-08-01；ID 1,201～2,000 为 2026-10-01。`events_archive` 起初为空，两张表结构相同，`id` 均为主键。

归档策略 #1 使用条件 `created_at < '2026-09-01 00:00:00'`，目标为同一实例的 `events_archive`。批次和事务大小均为 200，写入目标后删除源记录。`pt-archiver` 3.2.1 放在 `/opt/dbops/tools/pt-archiver-3.2.1` 独立目录；主机没有升级系统 Perl 或 libc 包。平台预检查返回 `ok=true`，主键检查和 dry-run 通过。

执行任务 #42 与归档作业 #1 均为 `success`。作业记录的扫描、归档和删除行数各为 1,200。随后直接查询 MySQL：

| 核查项 | 结果 |
| --- | ---: |
| 源表剩余 | 800 行，ID 1,201～2,000 |
| 归档表 | 1,200 行，ID 1～1,200 |
| 两表重复 ID | 0 |
| 两表合计唯一 ID | 2,000 |
| `payload` 与 ID 不一致 | 0 |

首次预检查发现 Server 接受 64 字符的 MySQL 标识符，Agent 归档动作却限制为 32 字符。修正 Agent 校验后，重新预检查通过；修正前没有执行归档。tx124 的 Agent 已更新并重新连接，原二进制保存在 `/usr/local/bin/dbops-agent.before-archive-20261004`。

本次验证了单实例、专用测试表的完整归档。生产大表、跨实例目标、长时间运行和故障后续跑仍需单独验收。失败作业可能已有部分批次提交，应以源表和目标表的实际数据核查，不能只看作业计数。

# DBOps 进展与产品审计

记录时间：2026-10-04 06:49（Australia/Perth）。审计范围为当前演示环境、前端源码、已提交的实机验收记录和 PR #1 的检查结果。这份记录用于安排下一轮开发，不代表生产验收。

## 当前进展

DBOps 已有可操作的演示环境。Server、SQLite、Web 和本地 Agent 在 Docker 中运行。在线向导可通过 SSH 纳管 Linux 主机。数据库服务页提供安装、启停、备份、恢复、复制和归档入口。任务中心保留步骤与事件，Oracle 实例页提供表空间及数据文件操作。

MySQL 是实机验收最完整的部分。clp01/clp02 完成双机安装、复制故障、逻辑和物理备份恢复、归档测试。tx50 完成单机两条 GTID 复制关系。tx50 到 tx124 完成跨主机 mysqldump 恢复。tx124 的任务 #38 一次完成自动 GTID 基线、传输、导入和复制登记；重启后继续同步。Oracle 19c 在 tx50 完成状态、表空间新增与扩容、RMAN 备份测试。

演示环境在审计开始时显示 7 个数据库实例全部离线、2/5 个 Agent 在线、13 条活动告警。tx50、tx124 和 tx180 的 Agent 服务仍在运行，三台主机的本地 `18089` 无法访问平台。本次恢复了文档中的反向 SSH 隧道。随后页面显示 7/7 个数据库在线、5/5 个 Agent 在线、0 个运行中任务。剩余 3 条活动告警为磁盘使用率超过 85% 的 P2 告警。六个远端 MySQL systemd 服务和 tx50 的 Oracle PMON 均处于运行状态。隧道是临时演示接入，断开后会再次影响监控。

PR #1 仍是草稿。当前提交 `1a88531` 的 8 项 GitHub 检查全部通过。工作区只有用户提供的 `reference/aio/` 未跟踪目录，本次审计未改动它。

## 优先改进项

### P0：先修状态与任务可信度

1. 区分“Agent 不可达”“监控数据过期”和“数据库进程已停”。本次隧道中断时，数据库列表统一显示 `offline`，但六个 MySQL 服务和 Oracle PMON 都在运行。实例、主机和 Agent 应显示最后检查时间、检查来源及断连原因。Agent 恢复后应明确标出等待下一次采集的状态。主机列表当前仍将失联 Agent 对应主机显示为 `online`。
2. 保证任务终态与步骤一致。任务 #36 已失败，详情里的 `DOWNLOAD_PACKAGE` 仍显示 `running`；任务 #35 已失败，进度却为 100%。失败或中断时，应关闭正在运行的步骤，并以终态文字解释进度。原始下载错误在任务列表中展示带 `sig` 参数的签名 URL，应在持久化和展示前遮盖令牌。
3. 为长时间软件包传输增加可见的字节进度、断点续传或可靠重试，并检查任务取消与超时行为。tx180 的任务 #36 因下载过慢和 Agent 断连而失败，未完成安装。再次测试前，先确认临时隧道、磁盘余量和软件包架构。

### P1：让 DBA 能从资源进入具体操作

1. 简化“资源中心 → 实例 → 操作”的路径。当前数据库服务页使用通用表单，安装时同时展示大量路径选项。默认只显示必要字段，展开高级设置；从实例详情进入时预选目标，并在提交前展示主机、端口、源与目标、备份范围和预检查结果。软件包列表按目标 Agent 的架构与系统筛选，离线 Agent 要标明不可提交的原因。
2. 修正实例详情的相关告警筛选。当前条件会把所有 `resource_type=database` 的告警显示在每个实例的“近期活动”中。应同时匹配资源类型和实例 ID，并提供跳转到对应告警的链接。
3. 让告警中心优先展示待处理项。现有默认列表把大量 `RESOLVED` 历史记录与活动告警混排，没有分页、资源名称或故障归因。按状态、级别、资源和时间筛选；Agent 失联引起的数据库采集失败应归并提示，避免同一网络故障生成整页 P1 告警。
4. 统一中文文案与状态展示。任务列表、步骤、事件、告警和记录页仍直接显示 `mysql.install`、`failed`、`FIRING`、JSON 字段名。保留原始代码供高级排障，在主要界面展示可读名称、目标实例、发生时间和建议动作。记录详情可以按备份、复制和归档分别设计，不再依赖动态字段表和原始 JSON。
5. 修复 Agent“最近心跳”空列。前端读取 `last_seen_at`，API 模型提供 `last_heartbeat_at`。首页请求尚未结束时会短暂显示全 0 和“当前运行平稳”，应使用加载占位，失败时显示加载错误。

界面层级继续保持紧凑。用户已明确不希望照搬参考 DBaaS 的大菜单。实例页只保留少量常用入口和与引擎相关的二级内容。

### P2：完成剩余能力与发布验收

1. 先确定 V1.0 的承诺范围。如果 V1.0 只覆盖 MySQL 与 Oracle 管理，就在导航与文档中明确 PostgreSQL、Doris 的试验状态；若全部引擎都属于 V1.0，则需增加真实集群和恢复验收。
2. 在测试环境演练 Oracle Data Guard 切换及 RMAN 恢复、MySQL 整机断电与网络分区。原主机物理恢复最终切换保留人工确认，并补齐操作指引和复核证据。
3. 补齐平台级备份恢复范围。当前离线工具恢复两个 SQLite 库，软件包、配置和密钥仍需单独保管。对象存储、长期保留、大表归档性能及生产负载压测另列专项验收。
4. 对整条 DBA 路径做浏览器回归：纳管主机、安装实例、建复制、备份、恢复、告警处置、任务失败与重试。覆盖窄屏、空数据、权限不足、Agent 断线和页面刷新。

## 建议的下一轮顺序

先修 P0 的状态语义、任务终态和敏感 URL 展示，再处理实例相关告警与心跳列。随后改造操作表单和告警/记录列表，最后补真实故障与恢复验收。每项改动都以演示环境复现、自动检查及对应实机证据作为完成条件。

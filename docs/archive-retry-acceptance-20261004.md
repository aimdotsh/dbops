# tx124 归档中断后的数据核查与重试验收

记录日期：2026-10-04。源为 tx124 MySQL 实例 #5（13310），目标为同一 Agent 管理的实例 #8（13314），仅使用新建的 `dbops_archive_retry_20261004` 测试库。测试时停止并恢复 tx124 的 `dbops-agent.service`；原有复制关系和业务表没有修改。

## 核查与变化拦截

第一组 `events` 写入 2,500 行，其中 2,000 行符合归档条件。策略 #5、任务 #51、作业 #6 在 Agent 断开后失败，平台最初计数为 0。Agent 恢复后，`reconcile` 确认旧归档进程退出、主键集合与执行前基线一致、两端无重叠，查出已提交 500 行，并将作业写入/删除计数各回填为 500。

核查后，向专用源表临时插入 ID 9999；重试接口重新核查后返回 HTTP 400，作业转为 `manual_review`，没有创建重试任务。删除这条测试记录、再次核查后，状态恢复为 `ready_to_retry`。随后任务 #52、作业 #7 归档剩余 1,500 行。此轮暴露了完成状态判断错误：数据已全部到达目标表，任务却被误报失败。修复后，对作业 #7 再次执行只读核查返回 `verified_complete`，不再允许重试。直接 SQL 核对为源表 500 行、目标表 2,000 行，合计 2,500 个唯一 ID，`payload` 无差异。

## 完整回归

第二组 `events_final` 写入 1,200 行，其中前 1,000 行符合归档条件。策略 #6 的任务 #53、作业 #8 在 Agent 断开后失败。只读核查查出已提交 250 行，并返回 `ready_to_retry`。确认后创建任务 #54、作业 #9，关联字段 `retry_of_job_id=8`；新作业成功归档剩余 750 行，状态 `success`、核查状态 `verified`。原作业 #8 保留失败状态及已核实的 250 行计数，以供审计。

直接查询两端：源表保留 200 行（ID 1001～1200），目标表有 1,000 行（ID 1～1000）。合计 1,200 个唯一 ID，没有重叠、缺失或 `payload` 内容差异。此结果同时验证失败任务的计数回填、固定归档条件、重试关联和最终任务状态。

## Server 重启恢复

第三组 `events` 写入 2,500 行，其中 2,000 行符合归档条件。任务 #55、作业 #10 执行期间强制终止演示 Server；此时目标表已有 1,700 行，Agent 上的归档进程随后退出。Server 重启后的租约恢复将任务标为 `interrupted`，同时把未完成作业标为 `interrupted/needs_review`，没有把 1,700 行误报为零，也没有自动重跑。

只读核查确认进程已退出、主键集合保持一致，并回填作业 #10 的 1,700 行。任务详情完成人工核查并释放中断任务后，作业 #11 作为 `retry_of_job_id=10` 成功补归档剩余 300 行。最终源表 500 行、目标表 2,000 行，2,500 个 ID 无重叠，`payload` 无差异。若在释放中断任务前调用重试接口，平台会直接拒绝，不创建排队中的重试任务。

## 适用范围

自动核查以执行前持久化的基线为依据，比较固定条件下的主键集合、匹配行数、两端主键重叠和旧进程状态。只对删除源记录、相同单列整数主键且匹配行总数不超过 50,000 的作业开放安全重试。该检查只覆盖键集合与行数，不验证所有非主键字段；测试的 `payload` 是另行用 SQL 核对的。相关表在核查和重试期间应停止其他写入。超限、旧作业无基线、无删除模式或核查失败时，按[运维流程](operations.md)人工处理。
